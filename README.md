# 腾讯云服务器抢购助手

腾讯云「上云精选 · 限时秒杀」轻量服务器（4 核 4G 3M，38 元/年）自动下单。

手动点「立即抢购」基本来不及，这个工具直接在活动页里调下单接口，Cookie 和 CSRF token 由浏览器自己带。

![界面截图](screenshot.png)

## 三步跑起来

1. `pip install -r requirements.txt`。只装 Python 包，浏览器用本机已有的 Chrome 或 Edge。
2. 双击 `腾讯云服务器抢购助手.bat`。它自己找本机的 Python，不用配路径。
3. 先选 **[2] 扫码登录**，再选 **[3] 开始抢购**（自动等最近一场），或 **[4] 选场次**。

抢到后订单保留 1 小时，去控制台付款，超时自动关闭。

活动页地址在 `seckill.py` 顶部的 `ACTIVITY_URL`。腾讯换活动页时改这一行就行，商品 id 是运行时现查的。

## 正式抢之前，先用 [5] 试一单

有些账号问题要到开抢那一刻才暴露：`600026`（没有创建实例权限）、`1100202`（要人脸核身）、`1100106`（实名主体已有付费记录，不算新用户）。等你在日志里看到这几种码，这一场已经过去了，白等十几分钟。

[5] 用 109 元专区商品走一次真实下单，不付款，能提前把这些坑试出来：

1. 菜单选 [5]，提示「确认真下单？」时输入 `YES`。
2. 看到「下单成功」并给出订单号，说明登录态、商品参数、首单资格、建单权限都通。
3. 去 [console.cloud.tencent.com/deal](https://console.cloud.tencent.com/deal) 找到这一单，取消掉。

**必须取消。** 它和 38 元那款是同一个首单 SKU，订单留着不取消，正式抢的时候会返回 `1100106`，等于自己把资格用掉了。

也别反复测。短时间反复建单会触发风控，被限制住可能第二天都抢不了。改过下单相关代码、或者第一次用的时候各测一次就够。

## 菜单

| 选项 | 说明 |
| --- | --- |
| [1] 地域设置 | 三地轮动并发（默认），或只抢上海 / 北京 / 广州其中一个 |
| [2] 扫码登录 | 扫码后自动保存登录态 |
| [3] 开始抢购 | 自动等待最近一场活动 |
| [4] 选择场次 | 指定 10:00 或 15:00 |
| [5] 测试下单流程 | 用 109 元专区商品真下单、不付款，测完记得取消 |

默认三地一起发，是因为查不出各地域是不是独立库存。这样做两种情况都不吃亏：总请求量不变，万一某个地域先没货还有机会。

能不能分清，看抢购日志里那行「库存判定」：比的是开窗这段里三地各自什么时候开始返售罄。某地先售罄、另两地还在打，或者三地售罄时间错得比较开，偏向各自有库存；三地几乎同时售罄，偏向一个总池。这只是线索，不是定论。

## 抢 10:00 还是 15:00

优先 10:00。上午服务端处理快，名额能撑到补发第二轮；下午 15:00 排队重，单条请求要等 2 秒上下，而名额差不多 2 秒就没了，几乎只剩开窗那一次机会。只抢一场就抢上午的。

两场用不同参数，程序自己切，不用你设：

| 场次 | 同时请求 | 持续 |
| --- | --- | --- |
| 10:00 | 35 起（开窗首发 30 条），按实测吞吐试到最多 64 | 10 秒 |
| 15:00 | 固定 55（开窗首发 50 条） | 12 秒 |

同时请求就是「发出去还没回来的请求最多几条」。为什么写 35 而不是 30：开窗前那几秒会先发几条探针量往返，它们和抢购请求共用这个额度，所以给 35 才能让开窗那一刻真的打出 30 条。

程序根据服务端回来的快慢自己调，10:00 场吃不下会自己退回去。下午场窗口太短，来不及试，所以直接固定。

你的网络往返超过 300ms 的话，下午场基本没戏，把机会留给上午。往返偏大时日志会打一行提示，照它说的换网络就行，不用改参数。

## 日志里的返回码

| code | 含义 | 该怎么办 |
| --- | --- | --- |
| `0` | 成功，已生成订单 | 1 小时内去控制台付款 |
| `1101001` | 秒杀尚未开始 | 正常，等场次；整场只报它说明商品 id 过期 |
| `1100106` | 实名主体已有付费记录，不满足新用户条件 | 换账号，继续抢没用 |
| `1100107` | 不满足活动参与条件 | 看活动规则 |
| `1100109` | 商品参数不对 | 提 issue 附日志 |
| `408` | 访问频率过快 | 开抢瞬间正常，程序继续 |
| `1100205` | 系统繁忙 | 服务端排队，程序继续 |
| `1100110` | 正在执行其他操作 | 同账号有单在提交，程序继续 |
| `1100136` | 当前商品已售罄 | 这个地域不再发；三个都售罄才停 |
| `1100202` | 账号需要人脸核身 | 账号级拦截，先去认证，程序停手 |
| `600026` | 账号没有创建实例的权限 | 子账号未授权 / 未实名 / 欠费，程序停手 |
| `1101408` | 接口层限流 | 和 `408` 一样处理，程序继续 |
| `-1` | 请求没发出去 | 偶尔几条正常；整场都是它检查网络 |
| `NOT-LOGINED` 等非数字码 | 登录态失效 | 重新扫码 |

收尾会打一行各码次数，比如 `408×180, 1100136×30`。`408` 多是被限流挡了，`1100205` 多是正常排队，出现 `1100136` 说明那个地域没名额了。

`1100202`、`600026`、`1100106/1100107/1100109` 是账号或资格问题，重试没意义，程序直接停本场。`1100136` 只摘掉返这个码的地域，三个都摘完才停。`408`、`1100205`、`1100110`、`1101001` 是开抢那几秒的排队信号，继续发。

## 常见问题

**扫好几次码才成功一次**

旧版有两个毛病：一是 cookie 要过几秒才下发，固定等 1.5 秒经常存到没有 `skey` 的空壳；二是 csrf 没带对时服务端返回 `400 CSRF-ERROR`，这其实说明 cookie 是有效的（真没登录是 `200 NOT-LOGINED`），旧代码却当成未登录，逼你重扫。现在盯着 `skey` 真的出现才存，`CSRF-ERROR` 也不再算失效。

菜单上的登录状态如实显示：`已保存（N 条 cookie）` 才算可用，`不完整（N 条，缺 skey）` 等于没登录，重扫一次。

**提示「未捕获到 CSRF token」**

这一版活动页改用 `Headers` 对象传头，旧写法取不到值。现在 `Headers` 实例、普通对象、数组三种都认，另外还有两层兜底（协议层嗅探、`g_tk` 现算）。三层都拿不到才会提示。

**一直返回 `1101001`**

活动时间窗内还报这个码，说明商品 id 过期了。程序会现查；日志出现「自动发现失败」是活动页地址也变了，改 `ACTIVITY_URL`。

**`1100106` 是不是程序出错**

不是。服务器原话是「相同实名认证主体已产生付费，不满足新用户条件」：这个实名主体只要有过付费记录就不算新用户，不限于这款商品。换账号才行。

要注意的是，资格预检查出来的 `user_available` / `idcard_available` 都是「是」也不代表能买，服务端临近开窗才做这层判定。

**换浏览器会影响登录吗**

不会。Cookie 从 `.state.json` 读，载入一个全新的隔离上下文，不碰你日常浏览器的数据。

**提示浏览器无法启动**

本机没检测到 Chrome 或 Edge，执行 `python -m playwright install chromium` 后重试。

**这一期活动结束还能用吗**

能。只要活动页打得开、查场次和查价格这两个接口还能调就行。腾讯换页了改 `ACTIVITY_URL`，必要时把新的 `activity_id` 加进 `CANDIDATE_ACTIVITY_IDS`。

## 它是怎么工作的

1. 读 `.state.json`，调一个只读接口确认登录态还有效，过期就重新扫码。
2. 打开活动页，注入 hook 抓前端动态算出来的 CSRF token。
3. 调 `/dianshi/get-now` 采样 7 次对时，取往返最快那次。本机时钟不准也补得回来。
4. 现查当天的场次和商品 id，再用 `query-price` 核对价格。
5. 开抢前 20 秒查一次资格，不合格当场中止，不白等一整场。
6. 开抢前 2 秒开始发，提前量按你实测的往返现算，之后回来一个补一个，三个地域轮着打。408 只记录，不缩量。
7. 读到 `0` 就停并给出订单号；账号类致命码立刻停手；某个地域售罄就摘掉它，三个都摘完才停。

## 反馈

抢到没抢到都欢迎开 issue，把 `seckill.log` 或控制台整段贴上来，别删括号里服务端的原话。只写「今天没抢到」看不出是名额没了、账号资格问题，还是被限流。这个项目基本是照大家的日志一轮轮改的。
