# 腾讯云服务器抢购助手

[![Python](https://img.shields.io/badge/python-3.10%2B-blue.svg)](https://www.python.org/)
[![License: MIT](https://img.shields.io/badge/license-MIT-green.svg)](LICENSE)

腾讯云「上云精选 · 限时秒杀」轻量应用服务器（4 核 4G 3M，38 元/年）自动下单工具。手动点「立即抢购」经常来不及，这个工具直接在活动页里调 `do-goods` 接口，Cookie 和 CSRF token 由浏览器自己带。

![界面截图](screenshot.png)

## 欢迎提交日志反馈

抢到没抢到，都欢迎开个 issue，把 `seckill.log` 或控制台整段贴上来。日志里有时序、对时偏移和每个返回码；只写「今天没抢到」，看不出是名额没了、账号资格，还是被限流。

贴的时候别删括号里的服务器原话，碰到没见过的码就靠它定性。抢到了也贴一份，不同机器、不同网络的日志能帮我判断提前量和并发该往哪调。

项目基本是照大家的反馈一轮轮改出来的，目标就是尽量提高抢购成功率。

## 三步跑起来

1. `pip install -r requirements.txt`。只装 Python 包，浏览器用本机的 Chrome 或 Edge。
2. 双击 `腾讯云服务器抢购助手.bat`。它自己找本机的 Python，不用配路径。
3. 先选 **[2] 扫码登录**，再选 **[3] 开始抢购**（自动等最近一场），或 **[4] 选场次** 指定 10:00 / 15:00。

抢到后订单保留 1 小时，去腾讯云控制台付款，超时自动关闭。

> 💡 **建议优先抢早上 10:00 那场。** 根据目前收到的实测反馈，10:00 场的成功率明显更高 —— 同样并发，10:00 场服务端响应约 0.94 秒，15:00 场要 3.9 秒，差 4 倍。场次越挤，你发出去的请求就越少。

活动页：https://cloud.tencent.com/act/pro/double11-202611#MS

> 地址每期会变，变了只改 `seckill.py` 顶部的 `ACTIVITY_URL` 一行；活动 id 和商品 id 是运行时现查的，不用手改。

## 开抢前先自检（强烈建议）

**正式抢之前，先用 [5] 试下一单，确认真能建单，然后立刻去控制台把订单取消。**

有些账号问题是到开抢那一刻才暴露的：等你在日志里看到 `600026`（没有创建实例权限）、`1100202`（要人脸核身）、`1100106`（已买过这款首单商品），那一场已经过去了，白等十几分钟。`[5]` 用的是 109 元专区商品，不受场次时间限制，随时能验，验完取消订单不花一分钱。

三步：

1. 菜单选 **[5]**，提示「确认真下单？」时输入 `YES`。会真的建一个订单（不付款）。
2. 看到「下单成功」并给出订单号，说明登录态、商品参数、首单资格、建单权限全都通，可以放心抢。
3. **马上取消这个订单**：打开 [console.cloud.tencent.com/deal](https://console.cloud.tencent.com/deal)（控制台 → 费用 → 订单管理），找到这一单 → 取消。

> ⚠️ **必须取消，别嫌麻烦。** 它和 38 元那款是同一个「首单」SKU，订单留着不取消，正式抢的时候会返回 `1100106 已购买此产品`，等于自己把首单资格用掉了。

> ⚠️ **别反复测。** 短时间反复建单会触发风控，有人被限制到第二天才能正常抢。只在改过下单相关代码后测一次，或者第一次用这个工具时测一次。

## 跑完看日志最后几行

| code | 含义 | 该怎么办 |
| --- | --- | --- |
| `0` | 成功，已生成订单 | 1 小时内去控制台付款 |
| `1101001` | 秒杀尚未开始 | 正常，等场次；整场只报它说明商品 id 过期 |
| `1100106` | 同一实名主体已买过 | 账号状态问题，换账号才有首单资格 |
| `1100107` | 不满足活动参与条件 | 看活动规则 |
| `1100109` | 商品参数不对 | 提交 issue 附日志 |
| `408` | 访问频率过快 | 开抢瞬间正常，程序继续 |
| `1100205` | 系统繁忙 | 服务端排队，程序继续 |
| `1100110` | 正在执行其他操作 | 同账号有单在提交，程序继续 |
| `1100136` | 当前商品已售罄 | 本场名额没了，程序停手 |
| `1100202` | 账号需要人脸核身 | 账号级拦截，先去认证，程序停手 |
| `600026` | 账号没有创建实例的权限 | 子账号未授权 / 未实名 / 欠费，账号问题，程序停手 |
| `1101408` | 接口层限流 | 和 `408` 一样处理，程序继续 |
| `-1` | 请求没发出去 | 偶尔几条正常；整场都是它检查网络 |
| `NOT-LOGINED` 等非数字码 | 登录态失效 | 重新扫码登录再来 |

收尾会打一行各码次数，比如 `408×180（系统访问频率过快）, 1100136×30（商品已售罄）`。`408` 占大头是被限流挡了，`1100205` 占大头是正常排队、纯拼名额，出现 `1100136` 就是名额没了。

`1100136`、`1100202`、`600026`、`1100106` / `1100107` / `1100109` 这几类重试没意义，程序直接停掉本场；`408`、`1100205`、`1100110`、`1101001` 是开抢那几秒的排队信号，继续发。

## 测试下单流程（[5]）

用「服务器专区」109 元商品走一次真实下单、不付款。它和 38 元那款配置相同但不是同一个商品，试它不会动到秒杀那款，能确认登录态、参数结构、首单资格和建单放行。

秒杀商品只在 10:00–12:00 / 15:00–18:00 能下单，窗口外只会返回 `1101001`，所以拿专区商品试。不付款的订单 1 小时后自动关闭、不扣钱，但还是请测完就取消 —— 什么时候该跑这一步、跑完怎么收尾，见上面的「开抢前先自检」。

## 常见问题

**Q：提示「未捕获到 CSRF token」**
活动页结构变了，hook 取不到 token。检查 `seckill.py` 里的 `CSRF_HOOK_JS`，或开 issue 附页面截图。

**Q：换浏览器会影响登录吗**
不会。Cookie 从 `.state.json` 读取，载入一个全新的隔离上下文，不碰本机日常浏览器的用户数据。

**Q：提示浏览器无法启动**
本机没检测到 Chrome 或 Edge，执行 `python -m playwright install chromium` 后重试。

**Q：一直返回 `1101001`，是不是坏了**
在活动时间窗内还报这个码，说明商品 id 过期了。程序会自动现查；日志出现「自动发现失败」就是活动页地址也变了，改 `ACTIVITY_URL`。

**Q：`1100106` 是不是程序出错**
不是，这是腾讯侧的业务规则：同一实名主体只能享受一次首单特惠，与程序无关。

**Q：这一期活动结束后还能用吗**
程序不依赖写死的 id：只要活动页能打开、`query-seckill-by-date` 和 `query-price` 还能调就能用。腾讯换了活动页就改 `ACTIVITY_URL`，必要时把新 `activity_id` 加进 `CANDIDATE_ACTIVITY_IDS`。

## 工作原理

1. **确认登录**　读 `.state.json`，调 `/dianshi/check-login` 验一遍，过期就重新扫码。
2. **加载活动页**　注入 hook 抓前端动态算出来的 CSRF token，这个没法离线拼。
3. **对时**　调 `/dianshi/get-now` 采样 7 次，按往返折半修正，取往返最快的那次；本机实测偏差 ±20ms，开抢前 3 分钟再校一次。本机时钟准不准无所谓，程序会补上。
4. **现查商品 id**　从页面取 `activity_id`，调 `query-seckill-by-date` 拿当天场次，再用 `query-price` 校验配置和价格。腾讯每期都换 id，写死就会一直返回 `1101001`。
5. **等**　开抢前 3 分钟刷新页面、复验登录、重新对时、再查一次商品；开抢前 20 秒发一个预检请求焐热连接，售罄或资格不满足就直接中止；最后 15 秒纯等待。
6. **开抢**　提前 2 秒进入发送阶段：先每 200ms 一条探针（最多 5 条在途）量往返，到「开窗前 单程 + 30ms」才把 20 条全放出去，之后回来一个补一个，持续 10 秒。
7. **出结果**　读到 `0` 就停并打印订单号；售罄、人脸核身或资格类致命码立刻停手；最后打一行各码次数。

提前量只是抵消请求在路上花的时间，不是越早越好——开窗前到服务端的请求只会拿到 `1101001`，白打还占限流额度。

如果日志里几乎只剩限流码，把 `ADVANCE_MS` 改成 `-1000` 再试；如果总觉得「我发的请求都比别人晚」，先把 `PRE_FIRE_MARGIN_MS` 调到 60~100，还不行再把 `PRE_FIRE_MAX_MS` 从 250 往上调（最多 600）——但注意调太高会让请求在开窗前就打到服务端，白拿 `1101001`。
